## 比较条件

同一runner、相同数据库、两条查询分别400/300次迭代、seed=29、检索宽24、
随机探索宽8、最大深度20；每组3次，新Python进程，交替先后顺序。
不清空OS文件缓存。NumPy固定2.2.6。不能直接拿不同runner的绝对秒数相除。
此处的优化前已经包含上一轮查询缓存，不是最初未优化版本。

主索引246,419条（精选11,843＋来源候选234,576）；本轮外部缓存15条。
TheoremSearch/arXiv 6、RealMath 6、zbMATH 3；S2ORC公开请求失败（HTTP 429）；详情保留在summary的prefetch。
没有加载MathPile或S2ORC全文，不能将六源接口解释为六源全量导入。

源码与数据指纹以summary.json为准，运行后数据库SHA256验证未变化。

## 内存指标的修正

上述24轮中旧peak_rss_kib_linux字段来自getrusage，所有进程均显示约691.77MiB。
复现实验确认：它继承了建库父进程在fork/exec前的高水位，不能用于后端内存比较。
原始数据保留，但该字段判为无效。已改为/proc/self/status的VmHWM，并独立补测。
补测数据另存memory_probe.json；不将单次补测伪装成3轮统计。
缓存本身上限64MiB，与整个进程的峰值RSS是不同指标。

### 独立内存补测（MiB，每场景一次）

[实际运行](https://github.com/ymd520/math-mcts-knowledge-tree/actions/runs/38708035019)；
8次运行全部完成，仍保持配对完整轨迹及最终路径一致，源文件指纹未变。
指标来自当前exec进程的VmHWM；这是单次补测，不是3次中位数。

不混用两次运行的绝对秒数。

## 使用与适用范围

可选安装：`python -m pip install -r requirements-acceleration.txt`。
安装后原research入口自动尝试加速；报告必须检查retrieval_profile.strategy及numpy_version。
没有NumPy时仍用标准库SQL路径，不自动联网安装，也不能套用本表提速倍数。
宽并列、显式领域筛选、内存异常和过大的rowid范围会回退SQL。
本结果仅覆盖这两条G5C查询、一个主索引规模及15条外部缓存，不能推广为所有任务都快3倍。
